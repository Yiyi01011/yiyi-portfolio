## 2. 项目背景

DesignSpark 是面向设计学生的 AI Agent Web App，目标是在设计早期最容易卡住的阶段帮助用户完成创意启动，并把每次创作过程沉淀为长期可复用的个人灵感资产。

设计学生常见的困难不是完全没有想法，而是拿到课程作业、竞赛题目、作品集项目或个人练习主题后，难以快速判断从哪里开始，难以把兴趣、生活观察、参考素材和视觉偏好转化为可执行的设计方向。传统聊天机器人可以回答问题，但往往缺少任务状态、长期记忆、阶段推进和灵感沉淀机制。

DesignSpark V1 将产品范围收敛为两个核心模块：

- 创意火花：帮助用户围绕当前设计任务与 Sparkie 对话，从模糊想法进入可继续制作的设计状态。
- 灵感地图：把历史会话火花和独立灵感捕捉沉淀为个人创意星系，帮助用户回看主题、关键词和视觉语言。

为什么这样设计：

- 设计早期最需要的不是自动生成最终作品，而是降低启动成本、帮助用户形成判断和下一步行动。
- 对学生而言，长期价值来自持续看见自己的兴趣和视觉语言，而不是一次性的回答结果。
- V1 优先验证“AI 引导创意启动 + 灵感沉淀闭环”，避免扩展成教学管理平台。

放弃了什么：

- 放弃教师端、班级、课程发布、作业批改等管理型功能。
- 放弃一开始就做完整 RAG、完整 Workflow 可视化、完整作品集管理。
- 放弃“AI 直接代做终稿”的定位。

## 3. 用户研究、已知事实与待验证假设

### 3.1 已知事实

以下为当前项目定义和代码实现能够确认的事实：

- 目标用户是需要完成课程作业、作品集项目、竞赛项目或个人练习的设计学生。
- 产品定位为个人化创意启动与灵感沉淀工具，不是教学组织或作业管理系统。
- V1 已实现登录、注册、会话创建、会话恢复、Coze Agent 对话、会话火花解析、灵感地图展示、独立灵感捕捉、个人设置等基础能力。
- 当前主 Agent 链路为 `/api/chat -> Coze Bot SSE -> 隐藏标记解析 -> Supabase 持久化`。
- 当前仓库无法确认 Coze 平台内 W01 到 W06 的真实 Workflow 拓扑、知识库绑定和发布状态。
- 当前没有真实用户调研数据、线上转化数据或自动化测试结果。

### 3.2 待验证假设

| 假设 | 说明 | 拟验证方式 |
| --- | --- | --- |
| 设计学生愿意在设计早期与 AI 进行多轮澄清 | 用户不是只想得到最终答案，而是愿意表达兴趣、卡点和偏好 | 观察会话轮次、澄清问题回复率、主动补充素材比例 |
| 阶段化 Agent 比普通聊天更能降低启动焦虑 | 五阶段进度和火花卡能让用户感到“正在推进” | 访谈、任务完成后自评、从首条输入到火花生成的完成率 |
| 灵感地图能形成长期回访价值 | 用户愿意回看历史火花，并从旧火花继续探索 | 灵感地图访问率、从火花详情发起新会话次数 |
| 图片和语音输入能降低表达成本 | 用户在无法准确描述风格时，会使用图片或语音补充 | 附件上传率、语音输入使用率、附件后会话完成率 |
| AI 不代做而是引导的边界能被用户理解 | 用户接受 Sparkie 不直接交付终稿，而是提供方向和行动建议 | 异常反馈、用户追问类型、对输出满意度访谈 |

### 3.3 不得虚构的数据

本文档不声明以下尚未真实获得的数据：

- 用户数量、活跃率、留存率、付费率。
- Agent 准确率、幻觉率、火花质量评分。
- 平均响应时间、线上成功率、Coze Workflow 命中率。
- 用户调研样本、访谈结论、竞品量化分析。

## 5. 问题定义

### 5.1 核心问题

设计学生在创意早期存在“启动困难”和“灵感难沉淀”的双重问题：

- 任务信息散乱：brief、限制、兴趣、参考素材无法快速结构化。
- 创意发散无抓手：用户常停留在空泛关键词，难以形成可执行方向。
- 个人偏好不可复用：每次项目从零开始，历史灵感没有反哺后续任务。
- AI 输出不可控：普通聊天容易直接给答案，缺少澄清、边界和阶段推进。

### 5.2 V1 解决的问题

DesignSpark V1 优先解决：

- 当前任务怎么开始。
- 如何把兴趣和素材转成火花。
- 如何把火花保存并回看。
- 如何让 Agent 在设计教育边界内引导，而不是代做。

### 5.3 V1 不解决的问题

- 不管理课程、班级、教师和作业发布。
- 不生成最终设计成品。
- 不承诺完整风格画像和真实长期 RAG。
- 不承诺所有文件类型都能被 AI 直接读取和理解。

## 6. 产品定位与价值主张

### 6.1 产品定位

DesignSpark 是面向设计学生的个人化 AI 创意启动 Agent 与灵感沉淀工具。

Sparkie 是产品中的 AI 创意引导 Agent。它不是普通 Chatbot，也不是一次性生成器，而是围绕任务状态、用户输入、历史火花和可保存灵感推进设计早期思考。

### 6.2 价值主张

| 价值 | 用户收益 | 产品实现 |
| --- | --- | --- |
| 降低启动成本 | 从空白状态进入行动状态 | 对话澄清、阶段进度、火花生成 |
| 提升表达清晰度 | 把模糊兴趣转为关键词、视觉语言和媒介转化 | 结构化火花字段 |
| 保留创意过程 | 不让有价值的过程性想法消失 | 会话历史、火花卡、灵感节点 |
| 形成长期风格线索 | 回看个人反复出现的主题和视觉偏好 | 灵感地图和主题聚类 |
| 保持用户控制 | AI 提供建议，用户选择是否继续、保存或调整 | 用户可发送、删除、归档、保存 |

| 会话历史 | 已实现 | 列表、恢复、重命名、归档、删除 |
| 会话火花卡 | 已实现 | 浏览会话内结构化火花，从火花继续探索 |
| 灵感地图 | 已实现 | 主题、火花、关键词、视觉语言图谱展示 |
| 独立灵感捕捉 | 部分实现 | 文字、图片、语音上传/分析/保存，依赖外部 AI 配置 |
| 方向/启动卡旧流程 | 部分实现 | 保留页面和 mock 数据，不作为 V1 主链路 |
| 风格档案和 RAG | 规划中 | 有表结构和文档，不作为已实现核心功能 |

### 8.2 关键取舍

#### 取舍一：从教学管理收敛到个人创意工具

为什么这样设计：

- V1 的核心验证对象是设计学生个人创意启动，而不是教学组织效率。
- 教师端会引入角色权限、课程结构、作业批改和组织关系，显著稀释 Agent 创意引导验证。

放弃了什么：

- 教师发布作业、学生提交作业、教师反馈、班级管理。

#### 取舍二：以自由对话为主，而不是固定表单流程

为什么这样设计：

- 设计早期输入天然模糊，固定表单会提高启动门槛。
- Agent 可以根据上下文决定追问、发散、捕捉或整理。

放弃了什么：

- 完全线性的任务创建向导。
- 每一步都强制填写完整字段。

#### 取舍三：优先沉淀火花，而不是生成终稿

为什么这样设计：

- 学习场景需要保留用户判断和创作主体性。
- 火花、关键词、视觉语言和行动建议更适合作为学生继续创作的起点。

放弃了什么：

- 直接生成完整视觉方案、最终海报、完整书籍或品牌系统。

#### 取舍四：保留旧方向页但不作为主链路包装

为什么这样设计：

- 旧页面可作为历史探索和辅助演示，但当前真实 Agent 主链路已经转向 `/api/chat`。
- 文档必须清楚区分已实现主链路和 mock 遗留链路。

放弃了什么：

- 把 `/api/agent/generate-directions`、`/api/agent/generate-card` 等 mock API 作为真实 V1 能力宣传。

## 10. 核心用户流程

### 10.1 首次使用流程

1. 用户访问首页。
2. 用户注册或登录。
3. 登录成功后进入 `/start`。
4. 用户选择“创意火花”或“灵感地图”。
5. 若选择创意火花，进入 `/spark` 并向 Sparkie 描述任务。
6. Sparkie 根据输入回复，并在合适时产生阶段进度和火花。
7. 用户可继续对话、查看火花卡或进入灵感地图回看。

### 10.2 创意火花流程

1. 用户输入题目、brief、模糊想法或素材。
2. 系统创建或续接会话。
3. 系统保存用户消息和附件。
4. Sparkie 分析上下文，进行澄清、发散、捕捉或整理。
5. 系统解析 Sparkie 隐藏标记，更新五阶段进度。
6. 如返回结构化火花，系统写入会话火花列表。
7. 前端展示消息、进度、火花入口和错误状态。

### 10.3 灵感捕捉流程

1. 用户在灵感地图中打开捕捉入口。
2. 用户输入文字，或上传图片、语音。
3. 系统上传素材并调用分析能力。
4. 系统生成灵感预览。
5. 用户确认保存。
6. 系统写入 `inspiration_nodes`。
7. 灵感地图刷新并展示新节点。

### 10.4 从灵感继续探索

1. 用户在灵感地图点击火花或灵感节点。
2. 用户查看详情。
3. 用户选择基于该火花继续探索。
4. 系统把火花上下文作为新探索种子传给 `/api/chat`。
5. Sparkie 开始新的独立会话，不直接继承原会话。

## 11. 功能需求详述

### 11.1 账号注册、登录与访问保护

| 项目 | 内容 |
| --- | --- |
| 状态 | 已实现 |
| 用户故事 | 作为设计学生，我希望拥有自己的账号，以便保存会话、灵感和个人设置。 |
| 前置条件 | 用户未登录或登录态有效。 |
| 触发条件 | 用户访问 `/login`、`/register` 或受保护页面。 |
| 正常流程 | 用户注册或登录；成功后进入 `/start`；受保护页面通过 middleware 和页面级鉴权。 |
| 异常流程 | 登录失败展示错误；注册需邮箱确认时跳回登录提示；登录态失效时 API 返回 401。 |
| 业务规则 | `/start`、`/spark`、`/inspiration-map`、`/settings` 必须登录；业务数据按 user_id 隔离。 |
| 页面反馈 | 登录/注册错误文案、注册成功提示、登录失效提示。 |
| 验收标准 | 未登录访问受保护页面跳转登录；登录后进入 `/start`；用户只能读取自己的数据。 |

为什么这样设计：

- 创意会话和灵感地图都属于个人长期资产，必须从 V1 开始建立账号和隔离。

放弃了什么：

- V1 不支持匿名长期保存，不支持教师或团队角色。

## 13. Agent角色、意图识别、澄清策略和方向生成机制

### 13.1 Agent 角色

Sparkie 的产品角色是创意引导 Agent：

- 帮助用户理解任务，而不是替用户完成作品。
- 帮助用户把兴趣转化为设计线索，而不是给唯一标准答案。
- 帮助用户捕捉和整理火花，而不是保存所有聊天内容。
- 在信息不足时优先澄清，而不是直接生成完整方案。

### 13.2 与普通聊天机器人的区别

| 维度 | 普通 Chatbot | Sparkie |
| --- | --- | --- |
| 目标 | 回答当前问题 | 推进创意启动状态 |
| 上下文 | 当前对话为主 | 当前任务、会话进度、火花、历史灵感 |
| 输出 | 文本回复 | 文本回复、阶段状态、结构化火花 |
| 结果 | 一次性答案 | 可继续深化和沉淀的创意资产 |
| 边界 | 容易代答 | 强调用户选择和设计教育边界 |

### 13.3 意图识别

| 意图 | 状态 | 识别依据 | 产品动作 |
| --- | --- | --- | --- |
| 新任务启动 | 已实现为主链路输入 | 用户描述题目、brief、想法 | 创建会话并进入理解阶段 |
| 补充信息 | 已实现 | 用户继续说明背景、限制、偏好 | 续接会话并更新上下文 |
| 请求发散 | 部分实现 | 用户要求更多方向或可能性 | 由 Coze Agent 决定输出 |
| 捕捉火花 | 已实现协议解析 | Agent 返回火花标记 | 写入 session sparks |
| 保存灵感 | 部分实现 | 用户在灵感捕捉中确认保存 | 写入 inspiration_nodes |
| 继续旧火花 | 已实现 | 用户从详情发起新探索 | 传入 seedSparkContext |

### 13.4 澄清策略

Sparkie 在信息不足时应优先澄清：

- 只问影响方向判断的关键问题。
- 单轮追问建议控制在 2 到 4 个。
- 不要求用户一次性填完整表单。
- 对模糊输入保持可继续推进，必要时给出可选方向而非阻断。

### 13.5 方向生成机制

V1 中方向生成主要由 Coze Agent 在主对话中完成。仓库中旧方向 API 仍为 mock，因此 PRD 仅将以下作为产品要求和部分实现能力：

- Agent 应基于任务、用户兴趣、限制条件和素材生成可发展方向。
- 方向不应只给空泛主题，应包含表达角度、关键词、视觉语言和下一步行动。
- 当用户要求比较方向时，Agent 应说明优点、风险、制作难度和表达潜力。
- 最终选择权属于用户。

| 验收标准 | 用户能从对话中获得可继续制作的结构化卡片，并可回看或继续探索 |

为什么这样设计：

- 设计启动卡不应是终稿，而应是从空白进入制作的行动工作单。

放弃了什么：

- V1 不把旧 mock 启动卡页包装为完整真实生成能力。

### 15.2 灵感地图

| 项目 | 内容 |
| --- | --- |
| 状态 | 已实现 |
| 数据来源 | 会话火花、独立灵感节点 |
| 展示形态 | 个人创意星系 |
| 节点类型 | Theme、Spark、Concept、Visual Language |
| 交互 | 点击、hover、详情、从火花继续探索 |
| 验收标准 | 图谱能区分数据节点和装饰元素；无数据时显示空状态 |

为什么这样设计：

- 灵感地图承接长期价值，让用户看见自己反复出现的主题和视觉语言。

放弃了什么：

- V1 不做手动复杂图谱编辑，不要求每条关系都持久化。

### 16.1 登录状态

| 状态 | 系统行为 |

| 注册需邮箱确认 | 跳转登录并提示确认邮箱 |

### 16.2 历史数据

| 数据 | 行为 |
| --- | --- |
| 创意会话 | 支持列表、恢复、归档、删除 |
| 会话消息 | 刷新后从 Supabase 恢复 |
| 会话火花 | 保存在 conversation context snapshot |
| 独立灵感 | 保存在 `inspiration_nodes` |
| 上传附件 | 保存到私有 Storage 并记录 assets |

### 16.3 空状态

| 页面 | 空状态要求 |
| --- | --- |
| `/spark` | 展示初始输入区，引导用户描述任务或想法 |
| 历史抽屉 | 无历史时提示创建新探索 |
| 会话火花页 | 无火花时提示继续与 Sparkie 对话 |

### 16.4 异常状态

| 异常 | 页面反馈 | 处理规则 |
| --- | --- | --- |
| 空消息且无附件 | 提示输入内容或添加素材 | 不创建无效请求 |
| 消息过长 | 提示长度限制 | 不调用 Agent |
| Coze 未配置 | 提示 Sparkie 服务尚未配置 | 用户消息可保留 |
| Coze 超时 | 提示稍后重试 | 返回可恢复 session |
| 网络失败 | 提示网络连接异常 | 移除乐观消息或恢复已有 session |
| 附件不支持 | 提示格式或大小错误 | 不上传 |
| 文档未传给 Agent | Sparkie 提示用户补充关键信息 | 不声称已读取 |

## 17. AI能力边界、幻觉约束、失败降级和用户可控性

### 17.1 AI 能力边界

Sparkie 可以：

- 理解用户输入的设计任务和卡点。
- 追问关键信息。
- 发散创意方向。
- 提炼关键词、视觉语言和媒介转化。
- 生成可继续制作的火花卡。
- 帮助整理可保存灵感。

Sparkie 不可以：

- 声称读取了未传入 Agent 的文档内容。
- 为图片补造画面中不存在的事实。
- 直接承诺完成最终设计作品。
- 将未经确认的用户偏好写成固定人格判断。
- 将旧 mock 方向或启动卡描述为真实 AI 生成结果。

### 17.2 幻觉约束

- 对附件能力不确定时，必须说明限制并请求用户补充。
- 图片分析只描述可观察内容和设计线索。
- 输出中不得出现内部分析、判断依据、用户分组等后台语言。
- 结构化火花解析失败不得替换可见回复。

### 17.3 失败降级

| 失败点 | 降级策略 |
| --- | --- |
| Agent 调用失败 | 保留用户消息，返回错误提示和可恢复 session |
| 隐藏标记无效 | 展示可见文本，不保存无效火花 |
| 上传失败 | 删除已上传残留文件，提示重试 |
| 分析失败 | 不创建灵感节点，提示用户稍后再试 |
| 会话读取失败 | 跳回 `/spark` 或跳过不可读会话 |

### 17.4 用户可控性

- 用户决定发送什么、是否继续对话、是否保存灵感。
- 用户可删除或归档会话。
- 用户可管理 Sparkie 引导偏好。
- 用户可删除账号。
- AI 只提供建议和结构化整理，最终方向由用户选择。

## 18. 非功能需求

### 18.1 安全与隐私

| 需求 | 状态 | 验收标准 |
| --- | --- | --- |
| 用户数据隔离 | 已实现 | RLS 限制用户只能访问自己的业务数据 |
| 私有文件存储 | 已实现 | avatars、inspiration-assets、task-assets 均为私有 bucket |
| 服务端密钥保护 | 已实现 | Coze Token、Supabase service role 不暴露到浏览器 |
| 删除账号 | 已实现 | 二次确认后清理私有 Storage 并删除用户 |

### 18.2 可用性

- 输入区应允许模糊表达，不强迫完整填写。
- 错误文案应使用用户能理解的语言。
- 空状态应引导下一步行动。
- 移动端和桌面端均应保持主要流程可用。

### 18.3 可靠性

- Agent 失败不应导致用户输入丢失。
- 上传失败应尽量清理残留文件。
- 无效隐藏标记不应导致页面崩溃。
- 会话恢复应以 Supabase 数据为准。

### 18.4 性能

当前无真实线上性能数据。拟观察：

- 首屏加载时间。
- `/api/chat` 平均响应时间和超时率。
- 图片/语音上传成功率。
- 灵感地图节点较多时的渲染流畅度。

### 18.5 可维护性

- V1 文档必须区分主链路和旧 mock 流程。
- 视觉层、业务层、Agent 协议和数据层的修改边界应清楚。
- Coze 隐藏标记协议变更必须同步前后端解析逻辑。

### 22.6 面试表达建议

在 AI 产品经理面试中，DesignSpark V1 可以重点表达为：

- 从大而全教学管理方案收敛到个人创意 Agent 的产品取舍。
- 将普通聊天升级为“状态推进 + 结构化火花 + 长期灵感资产”的 Agent 产品设计。
- 在 AI 幻觉和代做风险下，通过澄清策略、附件限制提示、用户确认保存和失败降级保持用户控制。
- 在 V1 中坦诚区分已实现能力、部分实现能力和外部平台待确认能力，体现产品边界意识。
